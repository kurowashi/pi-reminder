# ADR 0001: 既定の注入方法を `persistent` にする

- 状態: 採用
- 日付: 2026-10-16
- 対象: `src/config.ts` の `DEFAULT_CONFIG.mode` と不正値のフォールバック、`src/index.ts` の冒頭コメント、README の設定表と注入方法の表、`examples/reminder.example.json`、DESIGN.md「固有の原則」、既定値に依存するテスト

## 背景

- `transient` は次のリクエストの末尾にだけリマインダーを追加し、セッションに保存しません（README「注入の方法」）。
- Anthropic の公式ドキュメントは、tool use の途中で thinking ブロックを改変せずに返すことを求めています。
  以前のユーザーターンに注入した per-turn リマインダーを取り除くと、後続の thinking ブロックが無効になると説明しています
  （Anthropic docs「Thinking」「Extended thinking」）。
- 上の2点から、`transient` で注入した後の次のリクエストでは、前のユーザーターンの内容が変わる、と推論できます。
  この推論に対応する pi の挙動は未再現です。Anthropic の説明を pi に当てはめた推論です。

## 決定

- `mode` の既定値を `"transient"` から `"persistent"` にする。
- 省略された `mode`、不正な `mode` の値は `"persistent"` として扱う。
- `transient` は明示的に指定したときだけ使う。

## 理由

- 既定の注入方法は、利用者が設定を書かなくても選ばれる。その既定が thinking の整合を壊す可能性があるなら、利用者が気づかないまま失敗しうる。
- `persistent` はリマインダーをセッションに保存するため、前のユーザーターンの内容が後から変わらない。推論上は、この問題を避けられる。

## 却下した代替

- 既定を `transient` のままにし、README で警告する。
  警告を読まない利用者は既定のまま失敗しうる。既定の危険を文書で補う形になるため却下。
- thinking を使うときだけ `persistent` にする（既定はモデルに応じて切り替える）。
  利用者の設定とモデルの組み合わせで既定が変わり、挙動の予測が難しくなる。どのモデルが thinking を使うかを pi が判定する仕組みも必要になるため却下。
- `transient` を廃止する。
  短く一時的な注意を履歴に残さずに出す用途がなくなる。DESIGN.md が挙げる「軽い注意を履歴に残さず出す」選択肢を失うため却下。

## 帰結

- 既定では、注入のたびにコード上 continuation（追加のモデルリクエスト）が 1 回発生する。トークンとターン数が増える見込みだが、未計測。
- 既存の設定ファイルで `mode` を省略していた利用者の挙動が変わる。従来の動作にしたい場合は `"mode": "transient"` を明示する。
- 次のいずれかが起きたら、この決定を見直す。
  - pi 上で `transient` の後に thinking の無効化が再現した場合は、根拠が確定する。
  - 再現しなかった場合は、既定を戻す案を検討する。
  - 継続リクエストのコストが利用者に問題になった場合は、既定値を見直す。
